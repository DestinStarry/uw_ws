# 水下机器人 ROS 2 工程入门说明

更新日期：2026年11月3日。适用工作空间：`/home/zy/uw_ws`，即已取消 `uw_robot_core`、分开闭环与解算节点的版本。

这份说明帮助你看懂一条指令如何从手柄到达推进器，也帮助你找到代码、参数和排查入口。当前是 **7个包、5个业务节点、9个业务话题**。默认启动4个节点，启用IMU后是5个。机载电脑原来Python读取IMU已验证可用；新的ROS 2 IMU封装仍需要在机载电脑确认。

## 1 先看整条链路

主链路：Windows手柄 → TCP节点 → 闭环控制节点 → 正反解分配节点 → 串口节点 → STM32 → 推进器和舵机。
反馈链路：IMU通过USB进入机载电脑；深度从STM32串口进入机载电脑。两者送给闭环控制节点。

闭环控制回答“机器人现在偏了多少，应该施加多大合力和力矩”；解算回答“这组力和力矩，四台推进器和两组舵角应该如何配合”；串口节点负责把结果变成STM32认识的文本。

四个名词先记住：包是代码的分类目录；节点是运行中的业务程序；话题是节点之间传数据的通道；驱动是把硬件原始字节翻译成可用数值的程序。一个包可以没有节点，也可以装多个节点。launch是批量启动节点的配置文件，本身不算业务节点。

例如手柄向前推：TCP节点发布摇杆值；闭环节点按当前模式计算目标力和力矩；解算节点算出推力和舵角；串口节点转换编号与量程后发给STM32。与此同时，IMU反馈继续进入闭环。具体哪台推进器出多少力由当时姿态、目标和执行器限制共同决定。

## 2 七个包和五个节点

| 包 | 节点 | 负责什么 |
|---|---|---|
| uw_robot_interfaces | 无 | 定义消息和共用数据结构 |
| uw_robot_teleop | tcp_bridge_node | 接收手柄TCP，回传基础状态 |
| uw_robot_imu | imu_node | Python读取IMU并发布数据 |
| uw_robot_control | control_node | 姿态、角速度、定深与模式管理 |
| uw_robot_allocation | allocation_node | 正反解、舵角规划、推力分配 |
| uw_robot_hardware | hardware_node | STM32串口和深度数据 |
| uw_robot_bringup | 无 | 启动文件和参数配置 |

IMU是唯一使用Python的业务节点，其余四个业务节点用C++。Python写的launch和测试脚本不参与实物闭环计算。

`control_node` 读取手柄、IMU和深度，输出机体系六维目标 `[Fx,Fy,Fz,Mx,My,Mz]`。前三项是力，单位N；后三项是力矩，单位N·m。它不计算四台推进器的最终推力。

`allocation_node` 接收六维目标。反解与分配把目标变成四推力和两舵角；正解把这组推力和舵角再算回合力、力矩，用来检查实际可达效果。舵角规划在该节点的后台线程中运行，50Hz执行路径按当前估计舵角分配推力。后台线程不算另一个ROS节点。

`uw_robot_core` 已取消。纯算法函数分别放在control和allocation包内；两个包都可以独立测试。interfaces包只保存双方约定的数据格式。

## 3 IMU如何进入闭环

链路：IMU → USB串口 → YbImuLib → imu_node → `/imu/data` → control_node。

`YbImuLib` 负责接收和解析厂商串口协议，返回四元数、角速度和加速度。`imu_node` 读取这些数值，处理启动零点、时间有效性和单位，再封装为ROS标准IMU消息。传感器内部完成姿态融合。

| 当前设置 | 含义 |
|---|---|
| /dev/ttyUSB0 | 默认IMU设备名，以原实物程序实际使用的端口为准 |
| 115200 | 配套YbImuLib串口驱动的默认波特率 |
| 100Hz与六轴 | 当前配置的硬件输出频率和融合模式 |
| 2秒 | 建立姿态零点的采样时长，启动时需要保持水平静止 |
| 0.1秒 | 原始帧或四元数帧过旧，数据会被判为无效 |

SDK四元数顺序是 `[w,x,y,z]`；ROS消息按orientation的w、x、y、z字段分别赋值。角速度已经是rad/s，不能再重复从度转换。SDK加速度单位是g，ROS节点乘9.80665转成m/s²。

启动零点使当前输出相对启动姿态；这不是自动识别IMU安装方向，也不是标定绝对北向。当前代码没有通用安装外参旋转，传感器轴与机器人机体轴需要在实机核对。

你机载电脑已有可用的YbImuLib，可以继续沿用；本机Windows没有它不影响机载采集。按当前代码，没有这个库就不能采集。SDK的导入还依赖pyserial和smbus2，需由运行ROS节点的同一个Python环境找到。

原orange.10.20把处理后的状态放入共享字典，控制循环直接读取；现在通过 `/imu/data` 传给控制节点。原实物采集成功不等于ROS 2话题链路已在实物验证成功。

## 4 九个话题怎样连接

话题名就是数据通道名。下面只统计业务话题，不包含ROS自动生成的 `/rosout` 和 `/parameter_events`。

| 话题 | 发布方 | 接收方 | 传什么 |
|---|---|---|---|
| /control/request | TCP节点 | 闭环控制 | 摇杆和按钮 |
| /imu/data | IMU节点 | 闭环与TCP | 姿态、角速度、加速度 |
| /depth/state | 串口节点 | 闭环与TCP | 深度、深度变化率和有效性 |
| /control/wrench | 闭环控制 | 解算节点 | 目标合力、力矩和使能状态 |
| /robot/status | 闭环控制 | TCP节点 | 解锁状态、模式、反馈有效性 |
| /allocation/status | 解算节点 | 观察工具 | 规划状态与力矩回算结果 |
| /actuators/command | 解算节点 | 串口节点 | 四推力、两舵角 |
| /hardware/tx | 串口节点 | 观察工具 | 准备发出的STM32文本 |
| /hardware/rx | 串口节点 | 观察工具 | STM32回传的原始文本 |

理解三个观察点就能区分多数问题：`/control/wrench` 看闭环想要什么；`/actuators/command` 看解算最终给了什么；`/hardware/tx` 看发往STM32的文本是什么。话题存在不代表其中已有新数据；IMU默认关闭时，其他节点仍会订阅 `/imu/data`。

推进器顺序需要特别注意：算法内部是“1上、3下、2右、4左”；STM32接收顺序是“1上、2右、3下、4左”。hardware节点统一完成转换。推力以N表示，正向除33、反向除24.5；舵角以rad表示，除以π/2后才形成归一化串口值。

## 5 分清运行环境和启动模式

当前开发工作空间在WSL的 `~/uw_ws`。实际读取IMU和连接STM32，需要在连接硬件的机载电脑运行对应节点。机载电脑原来的Python程序可用，并不说明它已经具备ROS 2运行环境。部署时需准备适合机载系统的ROS 2环境，并重新编译源码；不能把WSL的x86构建产物直接搬给ARM板使用。

每个新终端先加载环境：

```bash
source /opt/ros/humble/setup.bash
source ~/uw_ws/install/setup.bash
cd ~/uw_ws
```

先理解结构，用默认模式：

```bash
ros2 launch uw_robot_bringup robot.launch.py
```

默认启动TCP、闭环、解算和串口四个节点。`imu=false`，`dry_run=true`，不会打开STM32物理串口。没有有效IMU时，闭环不能解锁。停止输出应为OFF。

机载环境准备好后，先只验证IMU，不启动推进器控制：

```bash
ros2 run uw_robot_imu imu_node --ros-args -p port:=/dev/ttyUSB0
```

另开已加载环境的终端执行 `ros2 topic hz /imu/data` 或 `ros2 topic echo /imu/data --once`。hz和不带--once的echo会持续运行，按Ctrl+C结束；带--once的echo读取一帧后退出。等待零点建立后再检查数据变化。

连IMU但保持STM32输出关闭：

```bash
ros2 launch uw_robot_bringup robot.launch.py imu:=true dry_run:=true
```

实机接线、方向和SDK检查完成后，输出模式为：

```bash
ros2 launch uw_robot_bringup robot.launch.py imu:=true dry_run:=false
```

最后一条会打开配置的STM32串口，不应当作普通软件演示命令。三个模式任选一个运行；避免同时启动多套节点或多个程序占用同一串口。

## 6 找代码改参数和排查问题

从工作空间根目录进入 `src`，按下面的职责找文件：

| 想看什么 | 位置 |
|---|---|
| 闭环公式与模式 | uw_robot_control/src/controller.cpp |
| 闭环订阅与发布 | uw_robot_control/src/control_node.cpp |
| 正反解和有界分配 | uw_robot_allocation/src/allocator.cpp |
| 舵角与分配状态 | uw_robot_allocation/src/allocation_controller.cpp |
| 解算通信与规划线程 | uw_robot_allocation/src/allocation_node.cpp |
| 串口文本与编号转换 | uw_robot_hardware/src/protocol.cpp |
| IMU采集与ROS封装 | uw_robot_imu/uw_robot_imu/driver.py和imu_node.py |
| 统一启动与参数 | uw_robot_bringup/launch和config目录 |

统一参数文件是 `src/uw_robot_bringup/config/robot.yaml`。闭环增益、定深和手柄超时看control_node区块；舵机速度、推力变化率、规划周期看allocation_node区块；STM32设备看hardware_node区块；IMU端口看imu_node区块。当前是启动时读取参数，改完需要重启。

| 看到的现象 | 先检查哪里 |
|---|---|
| IMU没有数据 | 原SDK能否用同一个Python导入，设备名是否正确、串口是否被旧程序占用 |
| A不能解锁 | /robot/status中的IMU有效性、JOY新鲜度；松开A后重新按 |
| 闭环有目标但没有推力 | /allocation/status是否WAIT_PLANNER，目标是否过期或规划失败 |
| 推力存在而实物不动 | dry_run是否关闭，串口是否打开，STM32实际接收什么 |
| 方向不对 | 核对物理编号、舵机方向和IMU轴向，再看控制参数 |

不要通过关闭数据超时或取消限幅来处理没有输出。先沿话题链路找到数据从哪一步开始异常。

## 7 停机保护和验证范围

系统按三段链路分别检查输入：闭环控制检查手柄和IMU；解算检查闭环目标；串口检查执行器指令。

| 检查位置 | 条件与行为 |
|---|---|
| control_node | JOY超过0.35秒，或闭环IMU超过0.1秒，锁定并输出禁用目标 |
| allocation_node | 目标超过0.15秒，输出禁用执行器；等待有效规划时零推力 |
| hardware_node | 执行器指令超过0.15秒，向STM32发送OFF |

停机、重新解锁和切模式会改变epoch；控制节点重启会改变session。这两个标记用于作废旧的后台规划结果。它们是状态标记，不需要在调参时修改。调度和串口传输会叠加时间，这些不是硬实时保证；STM32还应有独立命令超时保护。

| 已有证据 | 能说明什么 |
|---|---|
| 7包构建和4项单元测试通过 | 包依赖、主要算法与协议检查通过 |
| 150组分配回归通过 | 正解几何和固定角分配与原Python数值一致 |
| 180拍控制目标回归通过 | 隔离分配后，闭环目标与模式计算一致 |
| 虚拟串口链路通过 | 解锁到输出，以及IMU、JOY、上游目标断流和解算节点退出的保护已验证 |
| 机载原Python读取成功 | 原IMU硬件与原驱动链路可用，这是你提供的实机信息 |

新的ROS 2 IMU封装尚未在机载电脑实测；C++非线性舵角规划与原SciPy求解器的动态效果、真实带载舵速、机械方向和水下稳定性仍需验收。软件测试通过不能代替这些实机检查。

当前建议的阅读与操作顺序：先看第1至2节认清职责，再看第3节弄懂IMU，接着按第5节只测IMU；确认反馈数据后，再以dry_run观察目标、推力和串口文本，最后进入实机输出验证。
